DeepSpaceTelemetryReader.TelemetryCore — Module
TelemetryCore

Shared infrastructure of the simulation: configuration loading, schema-aware validation, storage governance (artifact estimation, budgets, retention settings), the accelerated mission clock and its persisted anchor, run provenance (event logs, snapshots, safesave rotation), and batch/segment I/O. Contains no routing logic — the queuing doctrine lives in Emitter and Receiver. The module's source is split by concern into the files of src/TelemetryCore/, included in dependency order.

DeepSpaceTelemetryReader.TelemetryCore.telemetry_settings — Function
telemetry_settings(cfg::AbstractDict) -> NamedTuple

Validated [telemetry] parameters: session_start::Time, session_duration::Second (session_duration_hours ∈ (0, 24]: the daily scheduler wraps Time arithmetic at 24 h), bandwidth_profile::String (one of BANDWIDTH_PROFILES), sigmoid_steepness, gaussian_sigma, max_batches_per_hour, max_inflight_batches::Int, min_link_factor, and range_million_km ≥ 0 (spacecraft–Earth range; 0 disables the light-time delay) with the derived round_trip_light_time_sec = 2 · range / c.

The link capacity is given either as max_batches_per_hour or as the rate pair downlink_kbps and onboard_data_rate_kbps (both > 0); the two forms are mutually exclusive, and the pair fixes the capacity in batches per hour through the batch content span of [physics]. nominal_batch_transfer_sec is the transfer time of one batch at full capacity; catch_up_ratio (downlink over production rate) and onboard_data_rate_kbps are NaN in the batches-per-hour form.

Bounds raise [CONFIG] errors. Absent keys take their defaults, so the snapshot of an older run still reads; validate_config applies the required-key policy of a live configuration.

Examples

julia> cfg = Dict{String,Any}(
           "telemetry" => Dict{String,Any}("downlink_kbps" => 230.0, "onboard_data_rate_kbps" => 75.0),
           "physics" => Dict{String,Any}(
               "data_source" => "synthetic",
               "sample_rate" => 4.0,
               "segment_duration_sec" => 60.0,
               "batch_size" => 10,
           ),
       );

julia> tel = TelemetryCore.telemetry_settings(cfg);

julia> round(tel.nominal_batch_transfer_sec; digits = 1), round(tel.max_batches_per_hour; digits = 1), round(tel.catch_up_ratio; digits = 2)
(195.7, 18.4, 3.07)

julia> tel = TelemetryCore.telemetry_settings(Dict{String,Any}("telemetry" => Dict{String,Any}("max_batches_per_hour" => 20.0)));

julia> tel.nominal_batch_transfer_sec, isnan(tel.catch_up_ratio)
(180.0, true)

DeepSpaceTelemetryReader.TelemetryCore.contacts_settings — Function
contacts_settings(cfg::AbstractDict) -> ContactsSettings

Validated [contacts] section — the ground-contact schedule layered on the daily window of [telemetry]; every key is optional and an absent section reproduces the plain daily window.

  • seasonal_extension_hours ≥ 0 (default 0): peak extension of the daily window, cosine-modulated over season_period_days > 0 (default 365.25) and peaking at season_peak_day_of_year ∈ [1, 366] (default 172); telemetry.session_duration_hours plus the extension may not exceed 24 h.
  • [[contacts.passes]] (start datetime, duration_hours > 0) or schedule_csv (columns Start, DurationHours; relative paths resolve against the current directory, then the project root) — an explicit, non-overlapping pass list that replaces the daily generator. The two forms are mutually exclusive.
  • [[contacts.exceptions]] (date, optional start, duration_hours ∈ [0, 24], 0 = missed pass): the window of that date verbatim, in place of the generated one; incompatible with an explicit schedule.
  • low_latency_enabled (default true), low_latency_capacity_fraction ∈ (0, 1] (default 1), and [[contacts.low_latency_periods]] (start, duration_hours > 0, optional capacity_fraction, label): extra contact windows at constant capacity outside the nominal passes. Periods triggered by [[events.markers]] (event_marker_settings) are appended, labeled by the marker.

Malformed entries raise a [CONFIG] error: a silently dropped pass or period invalidates the scenario.

The mission clock, and the only one. Mission time advances only while every component task is parked, jumping to the earliest requested wakeup, so a mission is a deterministic sequence of events for a given seed. now_sim is the current instant, horizon the mission end (start_sim_time plus mission_span_days), and wall_epoch the wall instant of the start. pace is the speed-up of a paced run (simulation.mode = "wall"), under which the driver releases a wakeup at logical instant t no earlier than wall_epoch + (t − start_sim_time) / pace of wall time, and catches up without sleeping when the host lags, so the content is that of the unpaced run; nothing for an unpaced run (--tick), which does not wait on the wall clock. DeepSpaceTelemetryReader.TelemetryCore.run_ticks! — Function
run_ticks!(clock::TickClock, tasks::Dict{Symbol,Task};
           on_task_failed = (name, task) -> nothing,
           heartbeats = Dict{Symbol,String}(), should_stop = () -> false)

The driver of the tick clock. It advances the clock to the earliest wakeup (ties broken by component priority, then by registration order), releases that task, waits until it parks again or ends, and repeats until no task is parked. The clock stops at the horizon: a later wakeup resumes there, where the component sees horizon_reached and leaves. A task that ended with an exception is handed to on_task_failed(name, task) once; the callback returns a replacement Task created by tick_spawn, which takes the name in tasks, or nothing. Runs on the calling task's thread.

On a paced clock (clock.pace set, simulation.mode = "wall") the driver sleeps, before each release, until the wall instant wall_epoch + (t − start_sim_time) / pace of the logical instant t, in chunks of at most 0.5 s; a host that lags releases at once and catches up. The sleep ends at once when should_stop() holds (the HALT sentinel or the stop flag), so the components, which check HALT at every wakeup, exit promptly. An unpaced clock never sleeps.

heartbeats maps component names to liveness files, present in both modes: the driver touches every file at the start, again after a release once HEARTBEAT_INTERVAL_MS have elapsed since the last touch (at most once per interval), and removes them when the mission phase ends.

DeepSpaceTelemetryReader.TelemetryCore.VisibilityModel — Type
VisibilityModel

Ground-contact model of the downlink. The nominal daily window opens at session_start for session_duration with the capacity profile (one of BANDWIDTH_PROFILES, shaped by sigmoid_steepness or gaussian_sigma; any other is an ArgumentError). seasonal_extension widens it symmetrically about its center, cosine-modulated with period season_period_days and peaking at season_peak_day_of_year. exceptions (date => (start, duration), zero duration for a missed pass) replace the window of a date verbatim, and a non-empty schedule of explicit passes replaces the daily generator. low_latency periods are additional windows at constant capacity outside the nominal passes. The three- to five-argument constructors build the plain daily model.

Examples

julia> model = TelemetryCore.VisibilityModel(Time(8), Second(8 * 3600), "sine");

julia> TelemetryCore.is_visible(model, DateTime(2035, 1, 1, 10)), TelemetryCore.is_visible(model, DateTime(2035, 1, 1, 3))
(true, false)

julia> round(TelemetryCore.profile_mean(model); digits = 3)
0.5
